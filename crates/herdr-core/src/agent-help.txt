hc (herdr-core) runs programs in terminals that keep going on their own. Use it to
- run commands: like bash (output, exit code), or in the background (servers)
- start other coding agents, talk to them, wait for their results
A person can attach to any terminal and take over.
You are $HC_TERMINAL_ID; what you start is your child. <t> = t7, t1b or a name.
Piped output is JSON, except run, read and file read (text).

Programs
  hc run cargo test                  waits like a shell: its output and exit code
  hc run "cd app && npm test"        one quoted string is a shell line
  hc run --bg --name web bun dev     start, don't wait: its end comes as a note, last lines in it
  hc wait web --output ready         until new output has "ready"
  hc read web --lines 100            its screen and 100 lines of history
After 180 s (--timeout S): "[hc] still running as t3", exit 124; it keeps going.

Agents
hc templates lists roles set up for you, maybe none. Use one if it fits:
  hc run --bg reviewer "review src/x.rs"   its instructions + task = first message
If none fits, start the agent yourself and say how to report back:
  hc run --bg claude "fix the failing test in x.rs. Done: hc send $HC_TERMINAL_ID"
Give the task in run: a booting agent drops a send (else hc wait <t> first).
Then:
  hc send t7 "fix the first one"     talk to it, busy or not
  hc read t7 --lines 200             what it wrote
  hc kill t7                         once its work is accepted
Work left? Keep at it: their messages and hc's notes reach you anyway.
Nothing left? Loop hc wait --children any, even for one child. It wakes on
a child's news or a message to you; reason message: its text is your next
input (maybe late), not for hc read. Wait again (it may still work).
Never sleep or poll.
hc wait <t> is for one terminal. Waits return status, not output: hc read <t>.
Messages arrive tagged; a template's first message says how to answer:
  <hc from="t3 lead" reach="hc send t3 when done or stuck">review src/x.rs</hc>
  <hc from="t7 reviewer">two bugs in relay.rs, see .local/review.md</hc>
Answer with hc send when done or stuck, not to acknowledge. hc ls lists all
terminals, not just yours. hc itself only speaks for a child that can't:
  <hc>t7 reviewer is blocked (permission). See: hc read t7</hc>   (or hit an error, or exited)

Other machines (over ssh or --via <cmd>; hc machine ls)
Your own read/edit/write tools only touch the machine you run on. To work on
another, hc is your hands: build and test with run/exec, files with hc file.
  hc run --on vps cargo test         -> vps/t3: use it like t3. Starts in its home (or --cwd)
  hc run --bg --on vps cargo build   long jobs: start, keep working; its end comes as a note
  hc exec --on vps git diff          exact output, no terminal: short commands (ls, mv, rm,
                                     grep); -i feeds it what you pipe in
  hc file read --on vps src/x.rs [--offset 200 --limit 100]
  hc file edit --on vps src/x.rs --old 'exact text' --new 'its replacement'
      old must be in the file exactly once (else edit_failed: add lines around it).
      Repeat --old/--new for several (all or none). Not sed: only the change travels.
  hc file write --on vps src/y.rs < content     a whole file, folders made
Paths: from its home or --cwd; without --on, from your folder.

hc keep <t> [--off] (or run --keep): replace lost programs with a shell, never re-run tasks.
Death by signal without an exit code is loss too. Recovery runs on every OS after a grace delay.
Streams end on loss; reattach after the restarted event. Pending input/attach: unavailable, retry.

Commands: run exec file ls get read send wait keys interrupt kill rm put label
keep templates attach machine. Details: hc <command> --help

Rules
- state: live or finished. status, the program's own word: idle working done
  blocked error. Plain programs report none: wait waits for them to exit.
- blocked = it waits on a person (permission, question). Read its screen,
  ask your user. send refuses unless --force.
- error = it failed (msg says why). Read it, then send or kill.
- wait reason timeout (default 180 s) is a check-in: wait again. So is
  not_started (send --wait: it hasn't begun); read it first.
- first_message.sent false: it never got ready and the task was NOT sent.
  hc read it; a trust dialog: hc keys <t> down enter. Then hc send the task.
- A failed send may still have arrived: read before resending.
- Report what workers wrote (hc read), not what you expect.
- Long answers: ask for a path.
- Never hc server stop unless asked: it ends all programs; kept terminals get shells at next start.
- Errors: {error: {kind, message, hint}} on stderr. Exit 3 not_found,
  7 needs_target, 9 blocked, 10 status_mismatch, 11 finished.
- Templates: ~/.config/herdr-core/templates/<name>.md: frontmatter name,
  description, command (with the model); body = instructions.
- Codex: run codex --no-daemon (templates too), or its commands run
  outside hc.
